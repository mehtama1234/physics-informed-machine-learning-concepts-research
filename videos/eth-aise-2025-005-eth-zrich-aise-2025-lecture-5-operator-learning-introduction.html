First-Principles Walkthrough

What this lecture is really about: Why solving equations backwards—learning operators instead of solutions

The question it answers: When you want to solve PDEs for many inputs, is it better to solve each one from scratch, or learn to recognize the pattern that maps inputs to outputs? And what does it even mean to do that with infinite-dimensional objects like functions?

Something concrete to hold onto: Imagine you're a weather forecaster. Every day you get a new map of today's temperatures and have to predict tomorrow's. Instead of running an expensive physics simulation each time, you watch a thousand past examples and learn to see the pattern yourself. That's operator learning—but mathematicians make it rigorous.

So far in this course, you've learned PINNs—physics-informed neural networks. They take the equation itself (like the Laplace equation) and use it as a teaching signal during training. You make guesses for the solution, compute the residual (how badly it violates the equation), and push that residual to zero. It's direct: equation-driven, no data needed. But it hits a wall when solutions have high frequencies or rapid changes—the training becomes exponentially harder because the optimization is poorly conditioned, like trying to solve a problem where the steepness of the landscape changes wildly. Preconditioning helps for simple 1D or 2D problems, but it barely dents the real issue.

The core limitation of PINNs is that they're glued to one question: 'Given this input (time, space, a source term), what is the solution *at this point*?' Mathematically, they're computing u(x,t) for fixed (x,t), point by point. But there's a richer way to think about PDEs. Most PDEs are systems: you give them an input (like a material property field or initial condition), and they produce an output (pressure field, velocity field). The relationship between inputs and outputs is deterministic and can be learned from data. This relationship is called a *solution operator*—a mapping from input functions to output functions. It's infinite-dimensional, because functions are infinite-dimensional (uncountably many points), but it encodes *system behavior*, not individual evaluations.

Here's a concrete example: subsurface flow (Darcy's law). The input is permeability—a spatially varying property of the rock. The output is pressure distribution. You could run an expensive finite element solver for each new permeability map, or you could gather data from many solves and train a network to recognize the mapping directly. Similarly, for compressible Euler equations in 2D, the input is an initial condition (density, velocity field), and the output is the solution at a later time. The operator maps the whole initial state to the whole later state. This is second-order thinking: not 'what's u at point x,' but 'what does this system do to this entire input function?'

Once you reframe the problem as operator learning, a natural question arises: can you just reduce it to finite dimensions? One naive answer is to parameterize your inputs. For airfoil design, instead of allowing arbitrary shapes, you fix a base shape and vary it using 20 basis functions (spline bumps). Now you have 20 parameters instead of a function. Train a network to map those 20 parameters to drag and lift. It works great—until someone needs 30 parameters to describe their design space. Your network, trained on 20 inputs, is useless. It doesn't generalize because even though shapes with 20 and 30 bumps might look visually similar, the parametrization doesn't respect that similarity. Parametrization is a strict jacket: it limits the space you can explore and kills generalization as soon as the parameters change.

So genuine operator learning must work with functions, not parameters. But you still need to use neural networks, which inherently work with finite-dimensional vectors. The solution is discretization: translate the infinite-dimensional problem into a finite-dimensional one in a way that respects the continuous structure. The simplest approach is 'discretize and learn.' You take your function input, sample it at a grid of points (say, 16 by 16 = 256 points in 2D). Pass those 256 numbers through an MLP. The MLP outputs 256 numbers (predictions at the same grid). Now you have a finite-dimensional map: R^256 to R^256, which you can train with standard neural networks.

But this 'discretize and learn' has three killer flaws. First: model size explodes. A 64-by-64 2D grid is 4,096 points. An MLP layer from 4,096 inputs to 4,096 outputs requires roughly 10-16 million parameters *for just one layer*. Move to 3D (64^3 = 262,000 points) and you need billions of parameters for a single layer. Your model becomes memory-prohibitive. Second: the points are treated as independent, losing spatial structure. Nearby grid points are highly correlated (smooth solutions vary slowly in space), but the MLP treats all 4,096 inputs as separate coordinates. This is wasteful and inefficient. Third, and most fundamentally: the network is bound to a fixed resolution. If you trained on 64-by-64 data, you can only evaluate on 64-by-64 data. Change to 128-by-128 and you can't use the network; the input dimension doesn't match. This isn't true operator learning, because a real operator doesn't care how finely you sample it—the underlying function-to-function mapping stays the same.

The resolution problem is the deepest issue. When you discretize to a grid and train on that grid, you're really learning a 'map from one specific discretization to another specific discretization.' If you refine the grid and add points between the old points, your network has no way to ingest that new information. You'd have to interpolate, but interpolation adds assumptions about what the function does between grid points—and that breaks the pure learning-from-data philosophy. Mathematically, the network is learning a map from R^n to R^n for a fixed n, not a genuine operator (which would be from function space to function space). You can change resolution in practice (by interpolating up or downsampling), but it requires post-processing tricks and isn't built into the architecture. Genuine operator learning means the model never 'sees' the points; it sees only functions and should work at any resolution automatically.

The next lectures will address this by building architectures that truly work on function spaces. Fourier neural operators encode functions as coefficients in a Fourier basis (infinite-dimensional), then apply learnable transformations in that basis, then decode back to function space. Graph neural operators discretize the domain into nodes but treat the discretization as incidental (a way to access the function), not fundamental. Attention-based operators learn position-invariant rules about how to process functions. These methods fix the resolution problem by building resolution-independence into the architecture itself. The goal is an operator learning approach where you can train on 64-by-64 data and confidently evaluate on 256-by-256 data, because you're truly learning the system's behavior, not memorizing a specific grid.

Key ideas in plain words

  • PDEs encode systems that map inputs to outputs—not individual points. Think of an operator as a function that eats a function and spits out a function, capturing how a system transforms entire fields.
  • PINNs solve equations point-by-point and struggle with high frequencies because training is ill-conditioned. Operator learning sidesteps this by learning from data instead of from residuals.
  • Parametrization (forcing infinite-dimensional inputs into 20 fixed parameters) seems like a shortcut but destroys generalization—as soon as your design space changes, the network becomes useless.
  • Discretization (sampling functions on a grid, training an MLP, interpolating the output) is simple but traps you: your network only knows the resolution it trained on, and changing grid size requires post-processing tricks, not genuine understanding.
  • True operator learning must be resolution-independent—the network should work automatically at any resolution because it learned the underlying function-to-function mapping, not a specific grid-to-grid mapping.
  • The cure requires new architectures (like Fourier neural operators) that work natively in function spaces and build resolution-invariance into the design, rather than bolting it on after the fact.
  • Infinite-dimensional thinking is hard with finite computers, but the key insight is this: you can discretize the learning process without discretizing the learning target—learn on discrete data without baking discretization into the model.

Worked intuition: Picture a 1D function on the interval [0, 1]: it might start low, spike in the middle, and drop at the end. An operator G transforms it (say, via diffusion) to a smoother version. Now, the naive approach: sample the input at 5 points (say, at 0, 0.25, 0.5, 0.75, 1.0), feed those 5 numbers to an MLP, get 5 output numbers, and interpolate. This works for that resolution. But what if you later want to sample the *same function* at 9 points (0, 0.125, 0.25, ...)? The 5-point MLP has no way to use the extra information in the two new points between the originals. It's bound to 5-point thinking. A true operator, though, would see 'this is a bump-shaped function' regardless of whether you describe it with 5 or 9 samples, because it's learning the smooth diffusion rule itself—spreading peaks outward smoothly—not a lookup table for a specific grid.

Where it breaks down: Discretize-and-learn breaks when: (1) you need high resolution (billion-parameter networks become impractical), (2) you want to generalize to untrained resolutions (your test data at 256x256 can't feed into a model trained on 64x64), and (3) you're trying to work with 3D+time data (memory and compute explode). It also fails philosophically—it learns a particular grid, not the underlying operator. For truly intricate systems (high-dimensional, chaotic, or multiscale), you need a better path.

Takeaway: Operator learning is learning the pattern *'what does this system do to any function input?'* rather than *'what is the solution at this point?'* Discretize-and-learn shows why you can't just reduce to finite dimensions naively—you lose resolution generalization and explode in model size. The cure is to design networks that truly work in function spaces, so that learning is untethered from a particular grid. This is the hard problem the course tackles next.

Video Study Note

Plain title: Why operator learning is a new step

Watch for: This lecture moves from solving one problem to learning a map between whole functions. Listen for solution operator, input field, output field, and family of PDE solves.

Main Points Discussed

  • A usual solver gives one answer for one input.
  • Operator learning tries to learn the rule that maps a new input function to a new output function.
  • The learned map is useful only when the family of inputs and outputs is named.

First-principles point: If the user needs many related solves, learn the map between problems and solutions, not only one solution.

Learner takeaway: Operator learning is about field-to-field maps. Keep asking what the input function is and what the output function is.

Do not worry about this yet: Do not start with Fourier layers or graphs. First understand what a solution operator is.
